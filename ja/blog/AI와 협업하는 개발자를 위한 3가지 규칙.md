---
title: "AIと協業する開発者のための3つのルール"
date: 2026-05-20
tags: [Tech, Troubleshooting, Incident Report]
---

AIを開発プロセスに導入することで生産性は劇的に向上しましたが、同時に新しいタイプの障害や技術的負債も経験しました。AIが生成したコードを検証なしに適用した結果、システム全体が不安定になるインシデントを経験した後、私たちはAIとの協業のための明確なガイドラインを確立しました。これは単なる推奨事項ではなく、安定したサービスのために必ず守るべき最低限の安全装置です。

### ルール1. AIの成果物を全面的に信頼しない。

AIは驚くほど速くコードを生成しますが、その成果物にはしばしば「幻覚（Hallucination）」現象が含まれます。これは、存在しないAPIを呼び出したり、かなり前に廃止された（deprecated）ライブラリの使用法を提示する形で現れます。

このようなコードをレビューなしでマージすることは、システムに予測不可能なバグを埋め込むことと同じです。したがって、AIが生成したすべてのコードは、新人開発者が作成したコードレビューリクエスト（Pull Request）のように扱うべきです。つまり、同僚レビューと同レベルの綿密な検証と単体テストが不可欠です。AIは優れた補助開発者に過ぎず、最終的な責任はコードをマージする開発者にあります。

### ルール2. すべての変更は構成管理を通じて記録する。

AIと協業する際、構成管理システム（Version Control System）、特に`git`の使用は選択ではなく必須です。AIが提案したコードを適用した際に、既存の機能が誤動作したり、潜在的な副作用が発見されたりすることはよくあります。

構成管理を通じて作業単位を明確にコミットしておけば、問題が発生した際にすぐに以前の安定した状態に戻すことができます。これは、AIの提案を恐れることなく実験し、適用できる心理的・技術的なセーフティネットとなります。問題のあるコードをデバッグするのに時間を浪費する代わりに、たった一行のコマンドでリスクを制御できます。

```bash
# 問題発生時、以前の安定したコミットに即座に復帰
git reset --hard <last_stable_commit_hash>
```

もしコミットを残していなかったら、どの変更点が問題を引き起こしたのかを特定するのに何倍もの時間と労力がかかったことでしょう。

### ルール3. ルール1とルール2を必ず守る。

3つ目のルールは、先の2つのルールの重要性を改めて強調するものです。開発過程でたった一度の例外（レビューの省略、コミットの漏れ）がプロジェクト全体を危険に晒す可能性があります。AI導入によって得られる生産性のメリットは、これら2つの基本原則を徹底的に遵守して初めて意味を持ちます。

結論として、AIは開発者の役割を代替するのではなく、変化させています。今や開発者の核となる能力は、コードを一から最後まで書く能力から、AIが生成したコードを**検証し、改善し、システム全体に安全に統合する能力**へと移行しています。この3つのルールは、変化する開発環境で安定性を確保するための最低限の規律です。
