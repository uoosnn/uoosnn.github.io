# ダウンタイムを最小限に抑えるRDSブルー/グリーンデプロイメント


## 課題：Aurora MySQLバージョンのEOS（End of Support）到来

運用中のAWS RDS Auroraクラスターのマイナーバージョンが間もなくEOS（End of Support）に到達する予定でした。EOSが到来すると、もはやセキュリティパッチやバグ修正のサポートを受けられなくなるため、安定したサービス運用のためにはデータベースのバージョンアップグレードが必須の状況でした。

単純なマイナーバージョンアップグレードではなく、サポート期間が長いLTS（Long-Term Support）バージョン（例：Aurora MySQL 3.10）へ移行し、今後数年間の安定性を確保することを目標としました。最大の課題は、サービスの中断、すなわちダウンタイムを最小限に抑えることでした。

## 解決戦略：AWS RDSブルー/グリーンデプロイメントの導入

ダウンタイムを最小限に抑え、安全なロールバックパスを確保するため、AWS RDSが提供する**ブルー/グリーンデプロイメント（Blue/Green Deployment）**方式を採用しました。この方式は、現在運用中のDB（ブルー環境）のレプリカ（グリーン環境）を事前に作成し、データ同期を維持しながら、最終的にトラフィックを一括で切り替える戦略です。

この戦略の核は、MySQLの論理レプリケーション機能である`binlog`を活用することです。

## 主要な前提条件：`binlog`の有効化

**RDSブルー/グリーンデプロイメント**は、ブルー環境で発生するすべてのデータ変更を`binlog`に記録し、これをグリーン環境に継続的に反映してデータを同期します。しかし、ほとんどの運用環境では、`binlog`はパフォーマンス上の理由から無効（`OFF`）になっていることが多いです。

したがって、ブルー/グリーンデプロイメントの作成を試みる前に、まずブルー環境（元のDB）のパラメータグループで`binlog_format`設定を変更する必要がありました。

```ini
# 対象: ブルー（元の）クラスターパラメータグループ
# 変更前: binlog_format = OFF
# 変更後: binlog_format = MIXED
```

`binlog_format`パラメータは`Static`タイプであるため、変更を適用するには**DBインスタンスの再起動が必須**です。サービスへの影響を考慮し、実際の移行作業に先立ってメンテナンス時間を確保し、事前に再起動を完了しました。この事前作業が、全体の**RDSブルー/グリーンデプロイメント**の成否を左右する重要なステップです。

## デプロイメント実行手順

### 1. ブルー/グリーンデプロイメントの作成

事前準備が完了した後、AWSコンソールで元のクラスターを対象に「ブルー/グリーンデプロイメントの作成」を開始しました。このプロセスでAWSは以下の作業を自動的に実行します。

1.  ブルー環境のスナップショットを作成。
2.  そのスナップショットを基に、目標LTSバージョンの新しいクラスター（グリーン環境）を構築。
3.  ブルー環境の`binlog`を利用してグリーン環境へのデータレプリケーションを開始し、リアルタイム同期状態を維持。

この作成プロセスは、データベースのサイズに応じて数十分以上かかる場合がありますが、ブルー環境のサービスには全く影響を与えません。

### 2. グリーン環境の検証

グリーン環境は、ブルー環境と完全に分離された独立したエンドポイントを持ちます。このエンドポイントを利用して、アプリケーションが新しいDBバージョンと互換性の問題がないか十分に検証しました。この段階で問題が発見されてもリスクはありません。単にグリーン環境を削除し、原因を分析してから再作成すればよいからです。

### 3. 切り替え（Switchover）

すべての検証が完了した後、トラフィックを切り替える「Switchover」を実行しました。この段階でのみ短いダウンタイムが発生します。切り替えプロセスは以下の通りです。

1.  ブルー環境へのすべての書き込み（Write）トランザクションを一時的にブロックします。
2.  ブルー環境に残っていた最後の`binlog`イベントをすべてグリーン環境に適用し、データ整合性を100%一致させます。
3.  既存のブルー環境が使用していたDBエンドポイントのDNSレコードをグリーン環境に変更します。
4.  グリーン環境が新しい本番DBとして書き込みトラフィックの処理を開始します。

これらすべてのプロセスは通常**1分以内**に完了し、ユーザーがほとんど認識できないレベルの短いダウンタイムだけで移行を完了することができました。

### 4. 事後措置

切り替えが成功裏に完了した後も、旧ブルー環境はすぐに削除されずに残ります。これは万が一の事態に備えた一種の保険であり、深刻な問題が発生した場合にロールバックのためのオプションとして活用できます。サービスが安定したことを確認した後、不要なコストが発生しないように旧ブルー環境を整理しました。

結論として、**RDSブルー/グリーンデプロイメント**は、`binlog`を活用した論理レプリケーションを通じて、ダウンタイムを最小限に抑えつつ安全にデータベースをアップグレードできる、非常に効果的な方法であることを改めて確認しました。
