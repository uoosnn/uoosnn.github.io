# Java4Shell(CVE-2026-114938) 脆弱性分析と段階的対応ガイド

::: tip 1行要約
OpenJDK 17.0.6以降でAVX-512 VBMIアクセラレーションを利用したBase64デコード時に発生するヒープバッファオーバーフロー(CVE-2026-114938)脆弱性は、最新ビルドにアップデートするか、JVMオプションに`-XX:-UseBASE64Intrinsics`フラグを追加することで解決できます。
:::

## 脆弱性の概要と攻撃メカニズム

CVE-2026-114938（通称 Java4Shell）は、JVMの低レベルハードウェアアクセラレーション最適化コードで発生するメモリ破損の脆弱性です。Oracle基準でCVSS 8.1、CVSS 4.0基準で9.2（Critical）に分類されています。攻撃は認証なしでリモートから可能であり、以下の段階で進行します。

1.  **悪性入力の送信**: 攻撃者が細工されたBase64エンコードデータを、認証不要なAPIエンドポイントなどに送信します。
2.  **出力長の誤計算**: OpenJDK内部のBase64デコーダーが、x86-64 CPUのAVX-512 VBMI命令最適化ルーチンを実行する過程で、デコード結果が保存される出力バッファの長さを実際よりも小さく計算します。
3.  **ヒープメモリの破損**: 割り当てられた配列の境界を超えて隣接するヒープメモリ領域を上書きするヒープベースのバッファオーバーフロー(Heap-based Buffer Overflow)が発生します。これにより、JVMクラッシュによるサービス拒否(DoS)攻撃や、隣接オブジェクトヘッダーの改ざんによるリモートコード実行(RCE)につながる可能性があります。

## 脆弱性露呈条件

以下のソフトウェアとハードウェア条件が**すべて満たされる**場合に脆弱性に露呈します。

*   **ソフトウェア**: OpenJDK 17.0.6以降のバージョン系列
    *   Java SE 17, 21, 25, 27 および GraalVM を含む
    *   *Java SE 8 および 11 バージョンは本脆弱性の影響を受けません。*
*   **ハードウェア**: x86-64アーキテクチャベースのAVX-512 VBMI命令セットをサポートするCPU
    *   *AWS GravitonなどのARM64アーキテクチャベースのCPUは、当該アクセラレーションコードを使用しないため安全です。*

## 段階的対応と緩和策

サービスのダウンタイム許容度に応じて、以下のいずれかの措置を選択して適用します。

### 1. 公式セキュリティパッチのアップデート (根本的解決策)

最も推奨される方法は、以下に明記された安全なビルドナンバー以上にランタイムを置き換え、サービスを再起動することです。

*   **Java SE 17**: 17.0.21.1+4 以降
*   **Java SE 21**: 21.0.13.1+4 以降
*   **Java SE 25**: 25.0.5.1+4 以降
*   **Java SE 27**: 27.0.1.1+4 以降
*   **GraalVM for JDK**: 17.0.21.1 / 21.0.13.1 以降

Eclipse Adoptium、Amazon Correttoなど、各OpenJDKディストリビューションのパッチリリーススケジュールは、ベンダーごとのセキュリティ勧告を確認する必要があります。

### 2. JVM起動フラグの変更 (一時的措置)

すぐにランタイムの置き換えが難しい場合、JVM実行オプションにフラグを追加して、Base64ハードウェアアクセラレーション機能のみを無効化できます。

```bash
java -XX:-UseBASE64Intrinsics -jar app.jar
```

この設定はプロセスの再起動が必要であり、Base64演算の比重が高いサービスでは、AVX-512アクセラレーション無効化による性能低下が発生する可能性があります。

### 3. 無停止一時緩和エージェントの適用

サービス再起動が不可能な環境では、Theori（ティオリ）が公開している無停止緩和ツールを使用できます。このエージェントは、実行中のJVMプロセスに動的にアタッチし、クラス再変換(Retransformation)を通じて脆弱なコードパスの呼び出しをブロックします。

ただし、メモリ常駐方式であるため、サーバーやプロセス再起動時に効果が失われるため、後で必ず公式パッチを適用する必要があります。

## 事後検証と点検事項

パッチ完了後、実際のランタイムに適用されたか、および過去の侵害痕跡(IoC)をクロスチェックする必要があります。

1.  **ランタイムパスの検証**: `java -version`コマンドの結果だけを信頼せず、`ps -ef | grep java`またはサービス起動スクリプトを通じて、実際の運用プロセスがパッチ適用済みのパスのJVMバイナリを参照しているかを確認します。
2.  **コンテナおよび組み込みソリューションの点検**: Docker環境では、ホストではなくコンテナのベースイメージを置き換えて再デプロイする必要があります。また、ERP、グループウェアなどパッケージ内部に含まれるEmbedded Javaは、ソリューションベンダー専用のパッチを適用する必要があります。
3.  **侵害痕跡(IoC)の調査**: パッチは今後の攻撃を防ぐだけであり、既存の侵害を復旧するものではありません。露呈期間中の異常な子プロセス生成、繰り返されるJVMクラッシュログ、不正な外部通信履歴などを点検する必要があります。

## 主要チェックポイント (Gotchas)

*   **ARM64環境でのx86専用オプション混用注意**: ARM64（AWS Gravitonなど）ベースのJVMは当該脆弱性の影響を受けず、`-XX:UseAVX`のようなx86専用オプションを認識しません。共通のデプロイスクリプトに当該フラグを一括挿入すると、ARM64ノードのサービス起動が失敗する可能性があります。
*   **例外処理(try-catch)の限界**: 細工されたBase64入力により`IllegalArgumentException`が発生しても、例外発生以前にネイティブデコーダールーチンがすでにヒープメモリを汚染している可能性があります。例外が処理されてもメモリ破損が残留し、その後のGC過程でJVMが異常終了する可能性があります。
*   **無停止エージェントの揮発性**: 無停止パッチエージェントはメモリパッチ方式であるため、オートスケーリングで新規インスタンスが生成されたり、プロセスが再起動されたりすると、脆弱な状態に戻ります。必ず根本的な解決策である公式ビルドアップデートに切り替える必要があります。
