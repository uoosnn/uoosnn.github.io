# 削除されたAWS SNSトピック復旧におけるARNの重要性


### 問題状況：削除されたSNSトピックと機能しないCloudWatchアラーム

最近、あるクライアント環境で、モニタリングアラームに使用されていたAWS SNS (Simple Notification Service) トピックが誤って削除されるインシデントが発生しました。最初に試みた復旧戦略は、削除されたトピックと「同じ名前」で新しいトピックを作成することでした。これは、CloudWatchアラームがトピックの「名前」を参照するという仮説に基づいた措置でした。

しかし、この方法は完全な解決策ではありませんでした。既存の多数のCloudWatchアラームが、新しく作成されたSNSトピックに正常に通知を送信できないという問題が発見されました。このトラブルシューティングログは、同じ名前でリソースを再作成したにもかかわらず、なぜサービス連携が失敗したのか、その原因である**ARN (Amazon Resource Name)**の概念と正しい復旧手順を記録するために作成されました。

### 初期対応と誤った仮説

削除されたSNSトピックの購読者情報を把握するため、まずAWS CloudTrailログを確認しました。`DeleteTopic`イベントは確認できましたが、該当トピックの作成または変更時点のログ（`CreateTopic`、`SetTopicAttributes`など）は、保存期間（90日）の満了により失われている状態でした。購読者リストをすぐに復元できない状況で、私たちは最も論理的に思える次の仮説を立てました。

> 「CloudWatchアラームはSNSトピックの『名前』を基準に通知を送信するだろう。したがって、同じ名前でトピックを再作成すれば、既存のアラーム設定を変更することなく、自動的に新しいトピックを認識して通知を送信するだろう。」

この仮説に基づき、削除されたトピックと全く同じ名前で新しいSNSトピックを作成しました。

### 根本原因：名前(Name)ではなくARN(Amazon Resource Name)

しかし、テストの結果、既存のCloudWatchアラームは依然として通知を送信できませんでした。原因は、AWSリソース管理の核となる概念である**ARN**にありました。

-   **名前(Name)**: ユーザーが指定する識別子で、リージョン内で一意ですが、削除後に再利用が可能です。
-   **ARN(Amazon Resource Name)**: AWSリソースが作成されるたびに付与されるグローバルに一意なIDです。リソースの「住民登録番号」のようなもので、一度削除されたリソースのARNは永久に消滅し、同じ名前でリソースを新しく作成しても、完全に新しいARNが割り当てられます。

CloudWatchアラームの「アクション(Action)」設定は、SNSトピックの名前ではなく、一意の識別子である**ARN**を保存します。

-   **既存のアラーム設定**: `arn:aws:sns:ap-northeast-2:123456789012:OLD-TOPIC-UNIQUE-ID`
-   **トピック削除**: 上記ARNは、もはや存在しないリソースを指すようになります。
-   **同じ名前でトピックを再作成**: `arn:aws:sns:ap-northeast-2:123456789012:NEW-TOPIC-DIFFERENT-ID` という新しいARNが付与されます。

結果として、既存のすべてのCloudWatchアラームは、依然として存在しない「過去のARN」を参照していたため、通知の送信が失敗していたのです。これが今回の**トラブルシューティング**の核心的な発見でした。

### 正しいSNSトピック復旧手順

今回のインシデントを通じて確立された正しい**AWS SNSトピック復旧**手順は以下の通りです。

1.  **購読情報の確保**: 最も重要なステップです。CloudTrailログが期限切れになっている場合は、IaC (Infrastructure as Code) コード、内部ドキュメント、またはサービス担当者を通じて、既存の購読者（Eメール、Lambda、SQSなど）リストを必ず確保する必要があります。今回のケースでは、幸い担当者が購読者情報を知っていたため、復旧が可能でした。

2.  **SNSトピックおよび購読の再作成**: 確保された情報に基づき、同じ名前のSNSトピックを新しく作成し、すべての購読を再度追加します。

3.  **CloudWatchアラームのアクション(Action)更新**: このステップが重要です。
    -   削除されたトピックを使用していたすべてのCloudWatchアラームを特定します。
    -   各アラームの「アクション」設定に移動し、存在しない以前のSNSトピック(ARN)を削除します。
    -   新しく作成したSNSトピック（新しいARN）を通知対象として再度追加し、保存します。

4.  **検証テスト**: すべての設定が完了した後、AWS CLIを使用して特定のアラームの状態を強制的に変更し、すべての購読者に通知が正常に受信されるかを確認します。

    ```bash
    # アラームの状態を強制的にALARMに変更してテスト
    aws cloudwatch set-alarm-state \
      --alarm-name "My-EC2-Status-Check-Alarm" \
      --state-value ALARM \
      --state-reason "Testing SNS notification recovery"
    ```

### 結論

今回の**トラブルシューティング**の経験は、AWSリソースを扱う際に「名前」と「ARN」の違いを明確に認識することがいかに重要であるかを示しました。多くのAWSサービス連携は、再利用可能な名前ではなく、不変の固有識別子である**ARN**に基づいて動作します。したがって、リソースを削除して再作成する際には、そのリソースを参照するすべてのサービスの設定を必ず確認し、新しい**ARN**に更新するプロセスが不可欠です。
