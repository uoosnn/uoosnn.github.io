## 문제 상황: 소리 없이 실패하는 Apache 실행

SSL 인증서 갱신 작업 후 Apache 웹서버가 기동되지 않는 현상이 발생했다. 일반적인 장애 상황과 달리 특이한 점은 다음과 같았다.

1.  **설정 파일 문법 오류 없음**: `httpd -t` 명령어로 설정 파일(`httpd.conf`)의 유효성을 검사했을 때, `Syntax OK`로 정상 응답을 받았다.
2.  **에러 로그 부재**: 메인 에러 로그 파일(`/var/log/httpd/error_log`)에 어떠한 오류 기록도 남지 않았다.

서비스는 실행되지 않는데, 원인을 파악할 단서가 전혀 없는 'Silent Failure' 상황이었다. 이런 경우, 프로세스 레벨의 동작을 추적하기 위해 시스템 콜을 추적하는 `strace`를 사용하기로 결정했다.

## 원인 분석: strace를 통한 시스템 콜 추적

아래 명령어를 사용하여 Apache 데몬이 포그라운드 모드(`-X`)로 실행될 때의 시스템 콜을 추적했다.

```bash
# strace /usr/sbin/httpd -X 2>&1 | tail -n 50
```

`strace` 출력의 마지막 50줄에서 프로세스가 종료되기 직전의 행적을 포착할 수 있었고, 이는 SSL 개인키 처리 과정에서 치명적인 오류가 발생했음을 명확히 보여주었다.

### 1. SSL Passphrase 처리 과정

```c
pipe([206, 207]) = 0
clone(...) = 2834
read(206, "8", 1)
read(206, "0", 1)
...
read(206, "\n", 1)
```

로그의 첫 부분에서 Apache는 `pipe`와 `clone` 시스템 콜을 통해 자식 프로세스를 생성했다. 이는 `httpd.conf`에 설정된 `SSLPassPhraseDialog` 지시문에 따라 암호화된 개인키의 암호를 외부 스크립트로부터 받아오기 위한 과정이다. `read` 시스템 콜을 통해 파이프로부터 암호 문자열을 성공적으로 수신한 것을 확인할 수 있다.

### 2. 개인키 파일 로딩

```c
open("/etc/httpd/ssl/key.pem", O_RDONLY) = 203
read(203, "-----BEGIN RSA PRIVATE KEY-----\r"..., 4096) = 1781
```

암호를 확보한 Apache 프로세스는 `open` 시스템 콜로 해당 가상 호스트의 개인키 파일(`key.pem`)을 열고, `read`를 통해 파일 내용을 메모리로 로드했다. 여기까지는 정상적인 흐름이었다.

### 3. 오류 발생 및 프로세스 종료

```c
write(46, "[Thu May 21 05:31:27 2026] [erro"..., 63) = 63
... (총 8줄의 에러 기록) ...
exit_group(1)
```

문제는 이 다음 단계에서 발생했다. Apache는 메모리로 읽어들인 개인키를 앞서 전달받은 암호로 복호화하거나, 복호화된 키를 인증서(`cert.pem`)와 비교하여 유효성을 검증하는 과정에서 실패했다.

주목할 점은 `write` 시스템 콜의 첫 번째 인자인 파일 디스크립터(File Descriptor)가 `46`이라는 점이다. 이는 표준 에러(`stderr`, fd 2)가 아닌, 해당 가상 호스트에 지정된 별도의 에러 로그 파일이었다. 즉, Apache는 **메인 에러 로그가 아닌 특정 가상 호스트의 로그 파일에만 오류를 기록**한 뒤, 오류 코드 `1`과 함께 `exit_group(1)` 시스템 콜을 호출하여 스스로 프로세스를 종료시킨 것이다. 이것이 메인 에러 로그에 아무런 흔적이 없었던 이유다.

## 결론 및 해결

`strace` 로그 분석을 통해 문제의 근본 원인을 다음 두 가지 시나리오로 좁힐 수 있었다.

1.  **개인키 암호(Passphrase) 불일치**: 새로 발급된 `key.pem` 파일의 암호가 변경되었거나 제거되었음에도, `SSLPassPhraseDialog` 스크립트는 이전 암호를 전달하여 복호화에 실패했다.
2.  **인증서와 개인키 페어(Pair) 불일치**: 개인키는 올바른 암호로 복호화되었으나, 함께 설정된 인증서 파일과 짝이 맞지 않는 경우. (즉, 두 파일의 모듈러스 해시값이 다름)

이 분석을 바탕으로, 새로 발급된 인증서와 개인키가 정확히 일치하는지 `openssl` 명령어를 통해 모듈러스 값을 비교하여 확인하고, 암호가 설정된 키라면 `SSLPassPhraseDialog` 설정이 올바른 값을 반환하는지 검증했다. 최종적으로 올바른 인증서/키 페어를 적용하고 Apache를 재시작하여 문제를 해결했다.

이번 트러블슈팅은 로그 파일에 단서가 남지 않는 장애 상황에서 `strace`와 같은 시스템 레벨 디버깅 도구가 얼마나 강력한지 다시 한번 확인하는 계기가 되었다.
