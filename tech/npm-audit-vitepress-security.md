# 🛡️ 정적 블로그(VitePress)의 npm 취약점 점검 및 대응 후기

사이드 프로젝트로 운영 중인 블로그나 개인 포트폴리오 사이트라도 의존성 패키지(npm)의 보안을 주기적으로 점검하는 것은 개발자의 훌륭한 습관입니다.
이번 포스트에서는 VitePress 기반의 제 블로그에 대해 `npm audit`을 돌려본 결과와, 이를 어떻게 해석하고 대응했는지 공유해 보겠습니다.

## 1. 정적 사이트에서 보안 점검이 굳이 필요할까?

최근 제 블로그의 CI/CD 파이프라인(GitHub Actions)을 점검하다가 이런 의문이 들었습니다.
> *"어차피 내 블로그는 GitHub Actions에서 빌드되어 정적 HTML로만 배포되는데, npm 패키지 취약점이 있다고 해서 진짜로 해킹당할 위험이 있을까?"*

**결론부터 말씀드리면, 런타임(웹사이트 접속 시) 해킹 위험은 0%에 가깝습니다.**
정적 사이트 생성기(SSG)인 VitePress는 빌드 과정에서만 Node.js 생태계(npm)를 사용하며, 최종 배포되는 것은 순수한 HTML/CSS/JS 파일뿐입니다. 따라서 서버 스크립트 실행 권한을 탈취하는 방식의 공격은 불가능합니다.

**하지만 무시해서는 안 되는 2가지 이유가 있습니다.**
1. **빌드 환경(CI/CD)의 위험**: 취약한 패키지가 악의적으로 깃허브 액션 컨테이너 내부의 환경변수(Secrets)를 탈취할 가능성이 존재합니다.
2. **로컬 개발 환경의 위험**: 내 PC에서 `npm run dev`를 돌리는 동안 디렉토리 횡단 공격(Path Traversal) 등을 통해 로컬 파일이 유출될 수 있습니다.

## 2. npm audit으로 취약점 스캔하기

블로그 루트 디렉토리에서 터미널을 열고 아래 명령어를 입력했습니다.

```bash
npm audit
```

그 결과, 무려 **6건의 취약점(High 4건, Moderate 2건)** 이 검출되었습니다.

### 주요 취약점 분석
* **brace-expansion (High, CWE-400)**: 조작된 입력으로 메모리를 고갈시켜 프로세스를 뻗게 만드는 서비스 거부(DoS) 취약점입니다.
* **postcss (High, CWE-22)**: `.map` 파일 로딩 시 경로 횡단(Path Traversal) 공격을 통해 서버의 임의 파일을 읽어갈 수 있습니다.
* **vite (High, CWE-22, CWE-522)**: Windows 환경에서 NTLMv2 해시(비밀번호)가 유출될 수 있는 치명적인 취약점입니다.

## 3. GitHub Actions가 알아서 다 해주는데 로컬에서 고쳐야 하나요?

블로그 배포를 GitHub Actions에 맡기고 계신다면, 저처럼 이런 의문이 드실 수 있습니다.
> *"GitHub Action에서 알아서 빌드하고 배포하는데, 굳이 내 PC(로컬)에서 취약점을 점검하고 고칠 필요가 있을까?"*

정답은 **"무조건 로컬에서 고치고 `package-lock.json`을 푸시해야 한다"** 입니다.

일반적으로 GitHub Actions 워크플로에서는 빠르고 일관된 빌드를 위해 `npm install` 대신 **`npm ci`** 명령어를 사용합니다. `npm ci`는 오직 우리가 올려둔 `package-lock.json` 파일에 적힌 버전과 **정확히 똑같은 버전**만 다운로드 받습니다.

즉, 우리가 로컬에서 취약점을 패치하여 `package-lock.json`을 업데이트해주지 않으면, GitHub Actions는 **백년만년 계속해서 취약한 구버전 패키지를 다운로드 받아 빌드**하게 됩니다.

## 4. 취약점 해결 및 대응 (npm audit fix)

해결 방법은 아주 간단합니다. 아래 명령어로 자동 치료를 진행했습니다.

```bash
npm audit fix
```

이 명령어를 치면 npm이 호환성을 깨지 않는 선에서 취약점이 패치된 안전한 마이너 버전으로 패키지들을 끌어올려 줍니다. 
저의 경우 이 명령어를 통해 3건의 High 취약점이 즉시 치료되었습니다.

일부 패키지(현재 `vite`와 `esbuild`)는 메이저 업데이트가 필요하거나 아직 상위 패키지의 패치가 나오지 않아 "No fix available" 상태로 남기도 합니다. 이런 경우엔 억지로 버전을 올리기보다, VitePress 공식 팀의 다음 업데이트 릴리스를 기다리는 것이 현명합니다.

## 마치며

블로그에 글을 쓰는 것만큼이나 중요한 것이 블로그를 지탱하는 뼈대(인프라)를 가꾸는 일입니다.
명령어 한 줄(`npm audit fix`)과 `package-lock.json` 푸시만으로도 훨씬 안전하고 단단한 개발 환경을 유지할 수 있으니, 지금 바로 여러분의 블로그 터미널 창을 열어 점검해 보시길 추천합니다!
