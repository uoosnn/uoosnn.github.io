## 문제 상황: Aurora MySQL 버전의 EOS(End of Support) 도래

운영 중인 AWS RDS Aurora 클러스터의 마이너 버전이 곧 EOS(End of Support)에 도달할 예정이었다. EOS가 도래하면 더 이상 보안 패치나 버그 픽스를 지원받을 수 없어, 안정적인 서비스 운영을 위해 데이터베이스 버전 업그레이드가 필수적인 상황이었다.

단순 마이너 버전 업그레이드 대신, 지원 주기가 긴 LTS(Long-Term Support) 버전(예: Aurora MySQL 3.10)으로 마이그레이션하여 향후 몇 년간 안정성을 확보하는 것을 목표로 설정했다. 가장 큰 관건은 서비스 중단, 즉 다운타임을 최소화하는 것이었다.

## 해결 전략: AWS RDS 블루/그린 배포 도입

다운타임을 최소화하고 안전한 롤백 경로를 확보하기 위해 AWS RDS에서 제공하는 **블루/그린 배포(Blue/Green Deployment)** 방식을 채택했다. 이 방식은 현재 운영 중인 DB(블루 환경)의 복제본(그린 환경)을 미리 생성하고, 데이터 동기화를 유지하다가 최종적으로 트래픽을 한 번에 전환하는 전략이다.

이 전략의 핵심은 MySQL의 논리적 복제 기능인 `binlog`를 활용하는 것이다.

## 핵심 전제 조건: `binlog` 활성화

**RDS 블루/그린 배포**는 블루 환경에서 발생하는 모든 데이터 변경 사항을 `binlog`에 기록하고, 이를 그린 환경에서 지속적으로 반영하여 데이터를 동기화한다. 하지만 대부분의 운영 환경에서 `binlog`는 성능상의 이유로 비활성화(`OFF`)되어 있는 경우가 많다.

따라서 블루/그린 배포 생성을 시도하기 전, 가장 먼저 블루 환경(원본 DB)의 파라미터 그룹에서 `binlog_format` 설정을 변경해야 했다.

```ini
# 대상: 블루(원본) 클러스터 파라미터 그룹
# 변경 전: binlog_format = OFF
# 변경 후: binlog_format = MIXED
```

`binlog_format` 파라미터는 `Static` 타입이므로, 변경 사항을 적용하기 위해 **DB 인스턴스의 재부팅이 필수적**이다. 서비스 영향도를 고려하여, 실제 마이그레이션 작업에 앞서 유지보수 시간을 확보해 미리 재부팅을 완료했다. 이 사전 작업이 전체 **RDS 블루/그린 마이그레이션**의 성패를 좌우하는 중요한 단계이다.

## 마이그레이션 실행 절차

### 1. 블루/그린 배포 생성

사전 준비가 완료된 후, AWS 콘솔에서 원본 클러스터를 대상으로 '블루/그린 배포 생성'을 시작했다. 이 과정에서 AWS는 다음 작업을 자동으로 수행한다.

1.  블루 환경의 스냅샷을 생성.
2.  해당 스냅샷을 기반으로 목표 LTS 버전의 새로운 클러스터(그린 환경)를 구축.
3.  블루 환경의 `binlog`를 이용해 그린 환경으로 데이터 복제를 시작하여 실시간 동기화 상태를 유지.

이 생성 과정은 데이터베이스 크기에 따라 수십 분 이상 소요될 수 있지만, 블루 환경의 서비스에는 전혀 영향을 주지 않는다.

### 2. 그린 환경 검증

그린 환경은 블루 환경과 완전히 분리된 독립적인 엔드포인트를 가진다. 이 엔드포인트를 이용해 애플리케이션이 새로운 DB 버전과 호환성 문제가 없는지 충분히 검증했다. 이 단계에서 문제가 발견되더라도 리스크가 없다. 단순히 그린 환경을 삭제하고 원인을 분석한 뒤 다시 생성하면 되기 때문이다.

### 3. 전환 (Switchover)

모든 검증이 완료된 후, 트래픽을 전환하는 'Switchover'를 실행했다. 이 단계에서만 짧은 다운타임이 발생한다. 전환 프로세스는 다음과 같다.

1.  블루 환경으로의 모든 쓰기(Write) 트랜잭션을 일시적으로 차단한다.
2.  블루 환경에 남아있던 마지막 `binlog` 이벤트를 그린 환경에 모두 적용하여 데이터 정합성을 100% 일치시킨다.
3.  기존 블루 환경이 사용하던 DB 엔드포인트의 DNS 레코드를 그린 환경으로 변경한다.
4.  그린 환경이 새로운 프로덕션 DB로서 쓰기 트래픽을 처리하기 시작한다.

이 모든 과정은 일반적으로 **1분 내외**에 완료되어, 사용자가 거의 인지하기 어려운 수준의 짧은 다운타임만으로 마이그레이션을 마칠 수 있었다.

### 4. 사후 조치

전환이 성공적으로 완료된 후에도 구(舊) 블루 환경은 즉시 삭제되지 않고 남아있다. 이는 만약의 사태에 대비한 일종의 보험으로, 심각한 문제가 발생할 경우 롤백을 위한 옵션으로 활용할 수 있다. 서비스가 안정화된 것을 확인한 후, 불필요한 비용이 발생하지 않도록 구 블루 환경을 정리했다.

결론적으로, **RDS 블루/그린 배포**는 `binlog`를 활용한 논리적 복제를 통해 다운타임을 최소화하면서 안전하게 데이터베이스를 업그레이드할 수 있는 매우 효과적인 방법임을 다시 한번 확인했다.
