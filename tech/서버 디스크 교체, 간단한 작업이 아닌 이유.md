# 서버 디스크 교체, 간단한 작업이 아닌 이유


서버 디스크를 교체하거나 데이터 경로를 변경하는 작업은 종종 "그냥 파일 옮기는 것 아니에요?"라는 질문을 받곤 합니다. 하지만 실제 현장에서 이 작업은 살아있는 서버의 심장을 잠시 멈추고 집도하는 대수술에 가깝습니다. 많은 분들이 간단하게 끝날 것이라 생각하지만, 실제로는 수많은 변수를 고려해야 하는 복잡하고 중요한 과정입니다.

이번 포스트에서는 서버 디스크 교체 및 데이터 마이그레이션 작업이 왜 간단하지 않은지, 그 이면에 숨겨진 네 가지 핵심 포인트를 짚어보겠습니다.

### 1. 데이터 정합성: '살아있는 생물'을 다루는 일

운영 중인 데이터베이스(DB)와 애플리케이션은 끊임없이 데이터를 읽고 쓰는 '살아있는 생물'과 같습니다. 이런 상태에서 무작정 파일을 복사하면, 복사 도중에 데이터가 변경되어 파일이 깨지거나(corrupt) 내용이 뒤죽박죽될 수 있습니다.

이를 방지하기 위해 **관련된 모든 서비스를 안전하게 중지시키는 과정이 필수적**입니다. 이는 마치 환자를 전신 마취하고 수술을 시작하는 것과 같습니다. 데이터의 일관성과 무결성을 지키기 위한 가장 기본적이면서도 중요한 첫 단계입니다.

### 2. 다운타임(Downtime): 서비스 중단 시간과의 싸움

서비스를 내린다는 것은 곧 장애 상황과 같습니다. 사용자의 불편을 최소화하기 위해 이 작업은 보통 이용자가 가장 적은 **새벽이나 주말**에 진행됩니다. 엔지니어는 남들이 쉬는 시간에 1분 1초라도 서비스 중단 시간을 줄이기 위해 수없이 시뮬레이션하고 자동화 스크립트를 준비하며 밤을 새우곤 합니다.

### 3. 권한과 소유권: '이 집은 내 집이 아니네?'

단순히 파일만 옮긴다고 작업이 끝나지 않습니다. MariaDB나 Oracle 같은 시스템은 `mysql`이나 `oracle`과 같은 특정 시스템 계정만이 데이터 파일에 접근할 수 있도록 엄격한 권한이 설정되어 있습니다.

만약 파일 복사 시 기존의 권한과 소유권 정보를 그대로 옮겨주지 않으면, 서비스는 재시작될 때 "내 데이터 파일인데 왜 읽지를 못하니!"라며 오류를 발생시키고 실행되지 않습니다. `cp -p`나 `rsync -a` 같은 옵션을 사용해 이 중요한 메타데이터까지 이전하는 세심함이 필요합니다.

### 4. '만약에'라는 변수: 롤백 계획의 중요성

숙련된 엔지니어는 항상 최악의 상황을 대비합니다.

- 만약 새로 장착한 디스크에 불량이 있다면?
- 만약 데이터 복사 중에 예상치 못한 에러가 발생한다면?
- 만약 시스템 설정(`fstab`) 실수로 서버가 부팅되지 않는다면?

이러한 '만약'을 대비하는 생명줄이 바로 **롤백 계획**입니다. 작업 전 원본 데이터를 `/mysql-data_old`처럼 백업용으로 남겨두는 것은, 문제가 발생했을 때 신속하게 원상 복구하기 위한 필수적인 안전장치입니다. 문제가 생겼을 때 되돌아갈 계획까지 모두 세워야 비로소 하나의 작업이 끝나는 것입니다.

이처럼 서버 디스크 교체는 단순한 파일 복사를 넘어, 데이터 정합성, 서비스 연속성, 시스템 권한, 그리고 비상 대응 계획까지 아우르는 고도의 전문성을 요구하는 작업입니다. 인프라의 안정성을 책임지는 엔지니어들의 깊은 고민과 노하우가 담긴 결과물인 셈입니다.
