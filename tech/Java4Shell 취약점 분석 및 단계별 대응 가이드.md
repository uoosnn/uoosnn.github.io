# Java4Shell(CVE-2026-114938) 취약점 분석 및 단계별 대응 가이드

::: tip 1줄 요약
OpenJDK 17.0.6 이상에서 AVX-512 VBMI 가속을 이용한 Base64 디코딩 시 발생하는 힙 버퍼 오버플로(CVE-2026-114938) 취약점은, 최신 빌드로 업데이트하거나 JVM 옵션에 `-XX:-UseBASE64Intrinsics` 플래그를 추가하여 해결할 수 있습니다.
:::

## 취약점 개요 및 공격 메커니즘

CVE-2026-114938(통칭 Java4Shell)은 JVM의 저수준 하드웨어 가속 최적화 코드에서 발생하는 메모리 손상 취약점입니다. 오라클 기준 CVSS 8.1, CVSS 4.0 기준 9.2(Critical)로 분류되었습니다. 공격은 별도의 인증 없이 원격으로 가능하며, 다음과 같은 단계로 진행됩니다.

1.  **악성 입력 전송**: 공격자가 조작된 Base64 인코딩 데이터를 인증이 필요 없는 API 엔드포인트 등으로 전송합니다.
2.  **출력 길이 오계산**: OpenJDK 내부 Base64 디코더가 x86-64 CPU의 AVX-512 VBMI 명령어 최적화 루틴을 실행하는 과정에서, 디코딩 결과가 저장될 출력 버퍼의 길이를 실제보다 작게 계산합니다.
3.  **힙 메모리 손상**: 할당된 배열의 경계를 넘어 인접 힙 메모리 영역을 덮어쓰는 힙 기반 버퍼 오버플로(Heap-based Buffer Overflow)가 발생합니다. 이로 인해 JVM 크래시를 통한 서비스 거부(DoS) 공격이나, 인접 객체 헤더 변조를 통한 원격 코드 실행(RCE)으로 이어질 수 있습니다.

## 취약점 노출 조건

아래 소프트웨어와 하드웨어 조건이 **모두 충족**되어야 취약점에 노출됩니다.

*   **소프트웨어**: OpenJDK 17.0.6 이후 버전 계열
    *   Java SE 17, 21, 25, 27 및 GraalVM 포함
    *   *Java SE 8 및 11 버전은 본 취약점의 영향을 받지 않습니다.*
*   **하드웨어**: x86-64 아키텍처 기반의 AVX-512 VBMI 명령어셋을 지원하는 CPU
    *   *AWS Graviton 등 ARM64 아키텍처 기반 CPU는 해당 가속 코드를 사용하지 않아 안전합니다.*

## 단계별 대응 및 완화 조치

서비스의 다운타임 허용 여부에 따라 다음 조치 중 하나를 선택하여 적용합니다.

### 1. 공식 보안 패치 업데이트 (근본 해결책)

가장 권장되는 방법은 아래 명시된 안전 빌드 넘버 이상으로 런타임을 교체하고 서비스를 재시작하는 것입니다.

*   **Java SE 17**: 17.0.21.1+4 이후
*   **Java SE 21**: 21.0.13.1+4 이후
*   **Java SE 25**: 25.0.5.1+4 이후
*   **Java SE 27**: 27.0.1.1+4 이후
*   **GraalVM for JDK**: 17.0.21.1 / 21.0.13.1 이상

Eclipse Adoptium, Amazon Corretto 등 각 OpenJDK 배포판의 패치 릴리즈 일정은 벤더별 보안 권고를 확인해야 합니다.

### 2. JVM 시작 플래그 변경 (임시 조치)

즉시 런타임 교체가 어려운 경우, JVM 실행 옵션에 플래그를 추가하여 Base64 하드웨어 가속 기능만 비활성화할 수 있습니다.

```bash
java -XX:-UseBASE64Intrinsics -jar app.jar
```

이 설정은 프로세스 재시작이 필요하며, Base64 연산 비중이 높은 서비스에서는 AVX-512 가속 비활성화로 인한 성능 저하가 발생할 수 있습니다.

### 3. 무중단 임시 완화 에이전트 적용

서비스 재시작이 불가능한 환경에서는 티오리(Theori)에서 공개한 무중단 완화 도구를 사용할 수 있습니다. 이 에이전트는 실행 중인 JVM 프로세스에 동적으로 Attach하여 클래스 재변환(Retransformation)을 통해 취약한 코드 경로의 호출을 차단합니다.

단, 메모리 상주 방식이므로 서버나 프로세스 재시작 시 효과가 사라지므로, 추후 반드시 공식 패치를 적용해야 합니다.

## 사후 검증 및 점검 사항

패치 완료 후, 실제 런타임에 적용되었는지와 과거 침해 흔적(IoC)을 교차 검증해야 합니다.

1.  **런타임 경로 검증**: `java -version` 명령어 결과만 신뢰하지 말고, `ps -ef | grep java` 또는 서비스 구동 스크립트를 통해 실제 운영 프로세스가 패치된 경로의 JVM 바이너리를 참조하고 있는지 확인합니다.
2.  **컨테이너 및 내장 솔루션 점검**: Docker 환경은 호스트가 아닌 컨테이너 베이스 이미지를 교체 후 재배포해야 합니다. 또한, ERP, 그룹웨어 등 패키지 내부에 포함된 Embedded Java는 솔루션 벤더사의 전용 패치를 적용해야 합니다.
3.  **침해 흔적(IoC) 조사**: 패치는 향후 공격을 방어할 뿐, 기존 침해를 복구하지 않습니다. 노출 기간 중 비정상적인 자식 프로세스 생성, 반복적인 JVM 크래시 로그, 비인가 외부 통신 내역 등을 점검해야 합니다.

## 핵심 체크포인트 (Gotchas)

- **ARM64 환경에서 x86 전용 옵션 혼용 주의**: ARM64(AWS Graviton 등) 기반 JVM은 해당 취약점의 영향을 받지 않으며 `-XX:UseAVX` 같은 x86 전용 옵션을 인식하지 못합니다. 공통 배포 스크립트에 해당 플래그를 일괄 삽입 시 ARM64 노드의 서비스 기동이 실패할 수 있습니다.
- **예외 처리(try-catch)의 한계**: 조작된 Base64 입력으로 `IllegalArgumentException`이 발생하더라도, 예외 발생 이전에 네이티브 디코더 루틴이 이미 힙 메모리를 오염시켰을 수 있습니다. 예외가 처리되더라도 메모리 손상이 잔류하여 이후 GC 과정에서 JVM이 비정상 종료될 수 있습니다.
- **무중단 에이전트의 휘발성**: 무중단 패치 에이전트는 메모리 패치 방식이므로 오토스케일링으로 신규 인스턴스가 생성되거나 프로세스가 재기동되면 취약한 상태로 복귀합니다. 반드시 근본적인 해결책인 공식 빌드 업데이트로 전환해야 합니다.
