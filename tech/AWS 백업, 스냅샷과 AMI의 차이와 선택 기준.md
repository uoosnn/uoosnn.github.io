특정 클라이언트로부터 EC2 인스턴스의 자동 백업 정책에 대한 문의가 접수되었다. 해당 논의 과정에서 우리는 내부적으로 표준화된 `AWS 백업` 전략, 특히 EBS 스냅샷과 AMI(Amazon Machine Image)의 기술적 차이점과 상황별 선택 기준을 다시 한번 명확히 정리했다. 이 기록은 당시의 분석 내용을 기술적 관점에서 정리한 로그다.

### 1. 백업 대상의 근본적인 차이

`AWS 백업`의 두 가지 핵심 방식인 EBS 스냅샷과 AMI는 백업하는 대상의 범위에서 근본적인 차이를 보인다.

*   **EBS 스냅샷 (EBS Snapshot)**: EBS 볼륨의 특정 시점에 대한 블록 레벨의 복사본이다. 이는 인스턴스에 연결된 가상 하드디스크, 즉 데이터가 저장된 볼륨 자체만을 백업하는 것을 의미한다. 운영체제(OS), 인스턴스 타입, 보안 그룹 설정 등 인스턴스의 구성 정보는 포함되지 않는다.

*   **AMI (Amazon Machine Image)**: 인스턴스를 실행하는 데 필요한 모든 정보를 포함하는 템플릿이다. AMI의 구성 요소에는 **하나 이상의 EBS 스냅샷**이 포함되며, 여기에 추가로 인스턴스의 아키텍처, 커널, 시작 권한, 그리고 블록 디바이스 매핑과 같은 인스턴스 메타데이터가 함께 패키징된다. 즉, AMI는 EBS 스냅샷을 포함하는 더 포괄적인 상위 개념이다.

### 2. 복구 시나리오 및 속도 비교

두 방식의 가장 큰 차이는 장애 발생 시 복구 과정(Recovery Procedure)에서 드러난다.

| 구분 | EBS 스냅샷 | AMI |
| --- | --- | --- |
| **복구 프로세스** | 1. 스냅샷으로부터 새 EBS 볼륨 생성<br>2. 새 EC2 인스턴스 생성<br>3. 생성된 인스턴스에 새 볼륨 수동 연결(Attach)<br>4. OS 레벨에서 마운트 작업 필요 | 1. AMI를 기반으로 새 EC2 인스턴스 즉시 실행(Launch) |
| **복구 속도** | 상대적으로 느리고 수동 개입 필요 | 매우 빠르고 자동화된 프로세스 |
| **주요 사용 사례** | 데이터 볼륨의 복제 및 마이그레이션, 파일 단위의 부분 복구 | 인스턴스 전체의 재해 복구(DR), 동일 구성 서버의 수평 확장(Scale-out) |

`EBS 스냅샷`을 이용한 복구는 여러 단계를 수동으로 거쳐야 하므로 작업 시간이 길어지고 휴먼 에러의 가능성이 존재한다. 반면, AMI를 통한 복구는 단일 API 호출 또는 몇 번의 클릭만으로 기존과 동일한 구성의 인스턴스를 완벽하게 재구성할 수 있어 복구 시간 목표(RTO)를 크게 단축시킨다.

### 3. 비용 구조 분석

비용 측면에서 중요한 사실은 **두 방식의 스토리지 비용은 동일하다**는 점이다. AMI는 내부적으로 EBS 스냅샷을 사용하여 볼륨 데이터를 저장하기 때문이다. 따라서 AMI를 생성하든, `EBS 스냅샷`을 직접 생성하든, S3에 저장되는 스냅샷 데이터의 용량에 대해서만 비용이 과금된다.

또한, AWS Data Lifecycle Manager(DLM)를 사용하여 백업 정책을 자동화하는 경우, DLM 서비스 자체는 무료로 제공된다. 결과적으로 백업 전략 선택 시 비용은 주요 고려사항이 아니며, 복구 목표와 운영 효율성에 초점을 맞춰야 한다.

### 4. 자동화 및 운영 표준: DLM 활용

우리는 모든 `AWS 백업` 정책을 AWS Data Lifecycle Manager(DLM)를 통해 관리한다. DLM을 사용하면 특정 태그가 지정된 인스턴스나 볼륨을 대상으로 백업 정책을 중앙에서 관리할 수 있다.

DLM 정책 설정 시, 생성할 백업 유형을 `EBS 스냅샷` 또는 `AMI` 중에서 선택할 수 있다. 이를 통해 우리는 운영 목적에 따라 정책을 유연하게 적용한다.

*   **재해 복구용 정책**: 매일 특정 시간에 인스턴스 태그를 기반으로 **AMI**를 생성하고, N일(예: 7일)이 지나면 자동으로 삭제하도록 설정한다.
*   **데이터 볼륨 보관용 정책**: 특정 데이터베이스 볼륨에 대해 매시간 **EBS 스냅샷**을 생성하고, 보관 주기에 따라 관리한다.

### 결론: 목적에 따른 전략적 선택

분석 결과, 두 기술은 상호 대체 관계가 아닌 명확한 목적성을 가진다.

- **인스턴스 전체의 가용성과 신속한 재해 복구**가 최우선 목표라면, 고민 없이 **AMI**를 표준 백업 방식으로 채택해야 한다. 이는 대부분의 프로덕션 서버 환경에 해당한다.
- **데이터 볼륨 자체의 이동, 복제 또는 특정 시점의 데이터만 분리하여 접근**해야 하는 특수한 경우에는 **EBS 스냅샷**이 더 유연하고 적합한 도구다.

따라서 우리는 클라이언트의 서비스 연속성 보장을 위해 기본 `AWS 백업` 정책으로 DLM을 통한 AMI 생성을 권장했으며, 이는 우리의 표준 운영 절차(SOP)와도 일치한다.
