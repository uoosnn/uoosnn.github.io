# PHP2Shell 취약점(CVE-2026-109619) 대응 및 완화 조치

::: tip 1줄 요약
PHP에서 메모리 부족(OOM) 발생 시 `longjmp()`로 요청이 중단되면서 내부 요청 데이터가 초기화되지 않아 발생하는 취약점(CVE-2026-109619, CVE-2026-109618)으로, 근본 해결을 위해 패치 버전 업그레이드가 필수적이며 즉시 패치가 불가한 환경에서는 php.ini 및 PHP-FPM 워커 재활용 설정, 요청 본문 크기 제한, WAF 룰 적용으로 공격 표면을 축소해야 합니다.
:::

## 취약점 발생 원인

CVE-2026-109619 및 CVE-2026-109618(통칭 PHP2Shell) 취약점의 핵심 원인은 PHP 엔진이 메모리 부족(Out of Memory, OOM) 오류를 처리하는 과정의 결함에 있습니다.

오류 발생 시, PHP는 `longjmp()` 함수를 호출하여 현재 요청 처리를 비정상적으로 중단합니다. 이 과정에서 내부 요청 데이터가 완전히 초기화되지 않고 메모리에 잔류하게 됩니다. 이후 동일한 워커 프로세스가 다음 요청을 처리할 때, 이전에 오염된 내부 상태가 그대로 재사용되면서 원격 코드 실행 등의 심각한 보안 문제로 이어질 수 있습니다.

EOL(End of Life)된 PHP 5.x 등 레거시 버전을 사용하는 서버가 주로 영향권에 포함되었으며, 근본적인 해결책은 지원되는 버전으로 업그레이드하는 것입니다.

## 단계별 완화 조치

PHP 개발팀과 보안 업계에서는 설정 변경만으로 공격을 완벽히 차단하는 것은 불가능하므로, 패치 버전으로의 업그레이드를 유일한 근본 해결책으로 권고합니다. 즉시 업데이트가 어려운 환경에서는 아래 4가지 임시 완화 조치를 조합하여 공격 표면을 줄여야 합니다.

### 1. PHP 및 PHP-FPM 설정 변경

세션 업로드 진행 기능과 자동 시작을 비활성화하고, OOM으로 오염된 워커 프로세스가 재사용되지 않도록 요청 1회 처리 후 프로세스를 재생성하도록 강제합니다.

- **php.ini 설정**
```ini
session.upload_progress.enabled = 0
session.auto_start = 0
```

- **www.conf (PHP-FPM) 설정**
```ini
pm.max_requests = 1
```

### 2. 웹 서버 요청 본문(Request Body) 크기 제한

공격자가 대용량 페이로드를 전송해 고의적으로 메모리 고갈(OOM)을 유발하는 것을 차단하기 위해, 웹 서버 단에서 허용하는 요청 본문 크기를 서비스에 필요한 최소치로 제한합니다.

- **Nginx (nginx.conf)**
```nginx
client_max_body_size 1m; # 서비스 특성에 맞는 최소 크기로 제한
```

- **Apache (httpd.conf 또는 .htaccess)**
```apache
LimitRequestBody 1048576 # 1MB
```

### 3. WAF 관리형 룰 적용

사용 중인 클라우드 및 네트워크 방화벽(WAF)에서 배포한 PHP2Shell 전용 긴급 차단 규칙을 활성화하여 비정상적인 페이로드를 사전에 필터링합니다.

- **대상 서비스**: AWS WAF, Cloudflare, Google Cloud Armor 등 각 벤더의 Managed Ruleset 업데이트를 확인하고 즉시 적용합니다.

### 4. 서드파티 어플라이언스 점검

일반 웹 서버뿐만 아니라 내부 관리 인터페이스 등에 PHP를 내장하여 사용하는 서드파티 어플라이언스 장비도 동일한 취약점의 영향을 받을 수 있습니다.

- **점검 대상**: Palo Alto Networks(PAN-OS), Siemens 등 PHP를 내장한 네트워크 및 보안 장비
- **조치 방안**: 각 제조사별 보안 권고문(Security Advisory)을 확인하여 전용 핫픽스를 적용해야 합니다.

## 핵심 체크포인트 (Gotchas)

- **임시 조치의 성능 영향도 고려**: PHP-FPM에서 `pm.max_requests = 1`을 적용하면 매 요청마다 워커 프로세스를 재생성하므로 CPU 오버헤드와 응답 지연이 발생할 수 있습니다. 이는 임시 방어용으로만 유지하고 조속히 코어 패치를 진행해야 합니다.
- **레거시 버전(PHP 5.x)의 한계**: 공식 보안 지원이 종료된 PHP 5.x 버전대는 공식 패치가 제공되지 않으므로, 임시 완화 조치 적용 후 PHP 8.x 등 지원 버전으로의 마이그레이션이 필수적입니다.
- **어플라이언스 장비 누락 주의**: 직접 구축한 웹 서버 외에 PAN-OS 등 서드파티 보안/네트워크 장비에 내장된 PHP 엔진이 보안 사각지대가 되기 쉬우므로, 자산 목록 기반의 전수 점검이 필요합니다.
