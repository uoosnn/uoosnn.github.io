Migrating an old legacy server to a modern environment involves many variables and complexities. This article outlines the step-by-step migration process and key considerations for moving a server running on an old MySQL and PHP environment to a new OS with MariaDB.

## Key Considerations Before Migration

Before starting the migration, there are two crucial points that must be confirmed and discussed with the client.

### PHP Upgrade and Web Source
When the server environment is upgraded, the existing web source (PHP) may not function correctly. Modifying the existing code to be compatible with the latest PHP version is not included in the scope of server migration support; this is the client's responsibility.

### Database (DB) Migration Path and Cost
Directly upgrading from the currently used MySQL 5.1 to the target version, MariaDB 11.4.2, is not possible. To ensure data integrity and stability, a multi-step migration process as outlined below is required.

```
mysql 5.1 -> 5.5 -> 5.7 -> 8.0 -> mariadb 10.x -> mariadb 11.4.2
```

As this involves a total of five sequential upgrade steps, it can incur significant time and cost.

## 4-Step Migration Execution Procedure

For a safe migration, the process is carried out through the following four steps.

### Step 1: Set Up a Temporary Server
First, a temporary server is prepared with the latest specifications requested by the client. The latest OS (e.g., Rocky Linux 9.x) and service versions (e.g., MariaDB 11.4.2) are installed, and an engineer proceeds with service integration.

### Step 2: Data Synchronization and Testing
All data from the original server (web source, DB data, etc.) is copied (synced) to the newly set up temporary server. The engineer verifies that the data has been imported correctly and performs multiple tests to ensure the service is operating normally. Afterwards, the client is guided on how to test from their local environment.

### Step 3: Modification and Re-verification (Nth Iteration)
If the client reports any functional problems or issues found during testing, the engineer will make the necessary corrections and improvements. This process may be repeated several times until the service is stable.

### Step 4: Final Migration
After receiving final confirmation from the client that all functions are working correctly, the final migration process begins.

*   **Service Downtime:** During the final migration, all web and DB services on the original server are stopped to prevent data loss and ensure complete data integrity.
*   **Final Data Synchronization:** With the services down, the DB data from the original server is copied to the temporary server one last time.
*   **IP Swap:** Once data synchronization is complete, the IPs of the original and temporary servers are swapped, redirecting service traffic to the new server.

This final migration process takes an average of 4-5 hours, but it may take longer if unexpected issues arise.
