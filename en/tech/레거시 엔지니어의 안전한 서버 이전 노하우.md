## Introduction: Have You Heard of a 'Legacy Engineer'?

I call myself a 'Legacy Engineer.' My main job is to safely migrate services for clients using old servers, released in the early 2010s, to a modern environment while minimizing downtime. In an environment fraught with hidden risks like outdated hardware, unsupported OSs, and old versions of PHP and MySQL, my role is to build a bridge that allows the client's business to continue without interruption.

In this article, I want to share the server migration know-how I've established through numerous projects, focusing on minimizing downtime and maximizing stability.

## Main Body: A 6-Step Process for Safe Server Migration

The biggest concern for clients is the anxiety of "What if the service stops or data is lost?" To alleviate this fear, I guide them through a systematic and transparent process that allows them to verify and gain confidence themselves.

### Step 1: Build the New Server Environment

First, I install a new OS on the new server. Then, I migrate the services used on the old server (like APM) to the same version or a newer version requested by the client.

### Step 2: Migrate the Latest Data

Once the environment is set up, I transfer the latest data, backed up via CDP early this morning, to the new server to ensure data consistency.

### Step 3: Provide a Perfect Test Environment for the Client

Before changing the actual DNS, I provide an environment where the client can test the new server's operation 100% with their actual domain. This works by modifying the local PC's `hosts` file to direct requests for a specific domain to the test server's IP.

**[How to Test on Windows]**

1.  Run Notepad as an **administrator**.
2.  Go to `File` -> `Open` and navigate to the `C:\Windows\System32\drivers\etc` path.
3.  Change the file type from `Text Documents (*.txt)` to `All Files (*.*)`.
4.  Open the `hosts` file.
5.  At the very bottom of the file, add a new line in the format `[Test Server IP] [Domain]` and save it.

    ```
    # localhost name resolution is handled within DNS itself.
    #       127.0.0.1       localhost
    #       ::1             localhost
    118.221.120.44 e-kflower.com www.e-kflower.com
    ```

Now, when you access `e-kflower.com` in your web browser, you will be connected to the new test server instead of the live production server.

> **Important:** After all testing is complete, you must delete the added lines to restore the `hosts` file to its original state.

### Step 4: Client Testing and Final Confirmation

Using the method above, the client meticulously tests whether all website functions operate normally under conditions identical to the live environment. Any issues found during this process are addressed immediately, and I wait for the client's final confirmation.

### Step 5: Final Migration (IP Swap)

After receiving the client's final confirmation, I perform a final data synchronization (Sync) during off-peak hours when service usage is lowest. Then, I swap the IPs of the old and new servers. This allows the client to use the upgraded server with the same IP and almost no downtime.

### Step 6: Post-Migration Management and Stabilization

Even after the IP swap is complete, I prepare for any unforeseen issues.
*   **Old Server:** It is kept for one week as a precaution in case there are problems with the new server, after which it is decommissioned.
*   **Old Backup Data:** To free up storage space, it is kept for two weeks and then deleted.

## Conclusion: Migrating Trust

Migrating a legacy system is not just about moving data. It's a role akin to a 'master system physician,' analyzing the business logic hidden in old code and configurations, diagnosing potential errors in advance, and safely modernizing the system.

By following this meticulous process, I turn a client's anxiety into trust and ensure a soft landing for their valuable business from an old, unstable infrastructure to a secure, modern environment. This is the pride of a 'Legacy Engineer.'
