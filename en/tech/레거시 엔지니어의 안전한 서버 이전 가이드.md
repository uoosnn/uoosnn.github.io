Legacy systems are a company's history and assets. However, technology is constantly evolving, and the time will come when they must be safely migrated to a modern environment. As a 'legacy engineer' who understands both past and present technologies to guide them safely into the future, I am sharing a systematic and secure server migration guide established through numerous experiences.

## Important Notices Before Migration

For a successful migration, understanding the state of the existing 'furniture' and clearly sharing the moving plan is as important as building a 'new house'. There are two key points that must be discussed with the client before starting the actual work.

### 1. Web Source (PHP) Must Be Modified by the Client.

Our role is to build a robust and stable new server (the new house) and transfer your data. However, the web source (the furniture) you were using may not be compatible with the new server environment. Specifically, if the PHP version is upgraded, the existing code may not function correctly and will require modification.

Such application code modifications are outside our scope of support, so the client must handle them directly.

### 2. The Database Requires a 5-Step Migration.

The currently used MySQL 5.1 version is too old to be migrated directly to the latest version, MariaDB 11.4.2. This is similar to transferring data from an old smartphone to a new one through several intermediate steps.

For a safe data transfer, a sequential 5-step migration is required as follows:

- **Migration Path:** `MySQL 5.1` → `5.5` → `5.7` → `8.0` → `MariaDB 10.x` → `MariaDB 11.4.2`

We inform you in advance that this multi-step process may incur significant time and cost.

## Safe Server Migration Procedure (4 Steps)

To minimize service downtime and ensure a safe migration without data loss, we follow this 4-step procedure.

### Step 1: Build a Staging Server (Building a Model Home)

First, we build a staging server that will act as a 'model home' by installing the latest OS (e.g., Rocky Linux 9.x) and service versions requested by the client. Then, our engineers configure all necessary services, such as web and DB, to be perfectly integrated.

### Step 2: Data Synchronization and Testing (Moving and Testing the Furniture)

All data from the source server (web source, DB data, etc.) is copied to the staging server. Our engineers verify that the data has been transferred correctly and guide the client on how to test the service locally. At this stage, the client can thoroughly check if all functionalities are working correctly.

### Step 3: Iterative Testing and Modification (Adjusting the Interior)

If the client reports any functional problems or issues found during testing, our engineers will immediately work on fixing them. This process of testing and modification can be repeated multiple times until the client confirms that "everything is perfect."

### Step 4: Final Migration (Changing the Signboard)

Once we receive final confirmation from the client that all functionalities are normal, we begin the actual migration.

- **Service Downtime:** To prevent data inconsistencies, we completely stop the web and DB services on the source server before the final data synchronization. The site will be inaccessible during this time.
- **Final Data Copy:** With the services down, we copy the DB data from the source server to the staging server one last time to ensure it is up-to-date.
- **IP Swap:** Once the data copy is complete, we swap the IP addresses of the source and staging servers. This directs all user traffic to the new server.

This final migration process takes **an average of 4-5 hours**, but it may take longer if unexpected issues arise.
