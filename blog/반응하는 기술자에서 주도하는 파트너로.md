# L2 스위치와 같았던 나: 반응하는 기술자에서 주도하는 파트너로

::: tip 핵심 인사이트
단발성 티켓 인입에 기계적으로 응답하는 'L2 스위치형 기술자'에서 벗어나, **시스템 구축부터 운영까지 컨텍스트(히스토리)를 쥐고 장애를 선제 예방하는 '주도적 파트너(Proactive Engineer)'**로 진화해야 한다.
:::

## 1. L2 스위치형 업무 패턴과 '컨텍스트의 부재'

수많은 고객사의 단발성 인프라 장애 티켓을 처리하는 일상은 네트워크 L2 스위치의 패킷 포워딩과 닮아 있었다.

* **현상**: 이슈 패킷 인입 ➔ 빠른 트러블슈팅 ➔ 다음 티켓으로 전환.
* **장점**: 다양한 이종 환경을 접하며 문제 해결 순발력과 CLI 감각이 극대화됨.
* **치명적 한계**: 해당 인프라의 과거 구축 배경, 레거시 변경 이력, 아키텍처 의사결정 컨텍스트가 완전히 결여되어 있어, 복합 장애 발생 시 근본 원인(Root Cause) 규명에 비효율적인 시간 소모가 발생.

```
[엔지니어링 업무 패러다임 비교]
Reactive (수동적 반응) : 장애 발생 ➔ 긴급 소화 ➔ 티켓 종료 (히스토리 단절)
Proactive (능동적 주도) : 아키텍처 설계 ➔ 변경 관리 ➔ 관측(Observability) ➔ 장애 예방
```

---

## 2. 두 가지 커리어 경로에 대한 고찰

### 1) 특정 시스템 전담 인하우스 엔지니어 (On-premise / In-house Specialist)
* **강점**: 시스템의 A부터 Z까지 살아있는 히스토리가 되어 다운타임을 최소화하고 오너십을 행사할 수 있음.
* **위험**: 서비스가 안정기에 접어들면 반복적인 유지보수 업무에 매몰되어 기술 스택의 확장이 둔화될 우려.

### 2) 클라우드 풀 라이프사이클 엔지니어 (MSP / Cloud Architect)
* **강점**: 고객 요구사항 분석부터 아키텍처 설계, IaC(Terraform) 구축, 운영, 최적화까지 **Full-Lifecycle 히스토리를 직접 생성**.
* **균형**: 다수의 도메인을 접하면서도 시스템 전반에 대한 엔드투엔드 책임을 유지할 수 있는 최적의 성장 모델.

---

## 3. 결론: Proactive 파트너로서의 지향점

내가 추구하는 엔지니어링의 본질은 "불이 났을 때 달려가는 소방수"에 머무는 것이 아니라, "화재가 발생하지 않도록 내진 설계와 스프링클러를 구축하는 아키텍트"가 되는 것이다.

트러블슈팅 경험은 단편적인 일회성 작업이 아니라, 시스템의 라이프사이클 전체를 이해하고 더 견고한 아키텍처를 설계하기 위한 귀중한 자산이다.
